# Phase 2 のデータと運用

## イベント設定

企画申請の `events.config` は次の形式で保存します。開始・終了日時は画面で日本時間として入力し、UTC に変換して保存します。

- 自由企画: `{}`
- ミッションビンゴ: `{ "size": 3, "missions": ["...", "..."] }`。`size` は 3 または 5、`missions` はそれぞれ 9 または 25 件です。
- IR: `{ "songs": [{ "game_title": "機種", "song_title": "曲名", "difficulty": "難易度" }], "intermediate_interval_hours": 24 }`。

## 集計の定義

- 曜日・時間帯は日本時間の開始時刻で分類します。深夜は 0〜4 時、午前は 5〜11 時、午後は 12〜17 時、夜は 18〜23 時です。
- 終了済みの承認・公開イベントを対象に、現在の有効部員を分母として集計します。過去の在籍状況は復元できません。
- 参加率・人数には `attending` と `late_early` を含め、遅刻・早退率には `late_early` を使います。種別別の平均人数はイベント単位で平均します。
- 学年・機種別は、各グループの現在の有効部員のうち、対象期間に1回以上参加した人の割合です。複数機種を登録した人は各機種に含まれます。
- 休眠者は終了済みの直近3イベントすべてで欠席または未回答の人です。終了済みイベントが3件未満の場合は抽出しません。
- Discord 通知先は送信時に再取得します。有効な数字のユーザー ID がない人にはメンションを送信しません。通知が複数回に分割され、一部で失敗した場合は送信済み件数を表示します。

## Supabase と Discord の前提

外部データベースへの接続・実環境での通知送信は行わず、共有されたスキーマと RLS、RPC を前提にしています。運用環境では特に以下が必要です。

- 有効な部員が自分を `created_by` とした `pending` イベントを作成できるポリシー。
- 役員・サークル長が `pending` イベントを参照し、承認または却下できるポリシー。
- 共有された出欠・メンバーの RLS と、トランザクション単位で処理する `bulk_upsert_members` RPC。
- イベント承認時の告知とリマインドを使用する場合は、サーバーに `DISCORD_WEBHOOK_URL` を設定します。未設定の場合、DB の承認は完了し、通知だけをスキップします。

自動テストは外部サービスを模擬します。実データに対する RLS、RPC、Webhook の結合確認は別途必要です。

```bash
docker compose exec web pnpm exec node --test tests/phase2.test.mjs
docker compose exec web pnpm lint
docker compose exec web pnpm build
```
